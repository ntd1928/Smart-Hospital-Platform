# AWS staging infrastructure

This CDK baseline defines an AWS network and application stack for Smart Hospital. It adapts AWS infrastructure patterns from Medplum's `packages/cdk` at commit `9cefcc93856c171cfacc630c7e8a66905919809f` (Medplum 5.2.14). Source attribution and the separate application runtime pin are recorded in [UPSTREAM.md](../../docs/architecture/UPSTREAM.md). The application remains on Medplum 5.2.7.

The CDK library and CLI are pinned to 2.278.0 and 2.1149.0. The upstream checkout uses an earlier CDK library; the infrastructure package uses the current patched release for its own code.

## What the stack creates

- A VPC with public, private application, and isolated data subnets. API and web tasks run without public IPs; one NAT gateway provides general outbound access and an S3 gateway endpoint keeps binary traffic on the AWS network.
- Two ECS/Fargate services built from the repository's `server` and `web` Docker targets. One Application Load Balancer redirects HTTP to HTTPS and routes `app.<zone>` and `api.<zone>` by host name.
- PostgreSQL 16 RDS with private access, client-enforced TLS, encryption at rest, generated credentials in Secrets Manager, seven-day automated backups, deletion protection, and retained storage.
- A private Redis OSS replication group with TLS, AUTH token in Secrets Manager, and a one-day snapshot window.
- A versioned, private, TLS-only S3 bucket used by the API's FHIR Binary storage. Binary uploads stream through the authenticated FHIR API; downloads use short-lived S3 presigned URLs. The ECS task role can read, write, and delete only objects under `binary/*`, and bucket CORS allows the configured app hostname. Local and Docker configurations continue using filesystem storage and signed `/storage` routes.
- CloudWatch log groups, VPC flow logs, a basic API target health alarm, and Route 53 aliases.

This is a staging foundation, not a production availability design. It uses one NAT gateway, a single-AZ database, one Redis node, and one task per service by default. It does not create a CI/CD pipeline or deploy itself. Running it creates billable AWS resources. No real patient data should be used until the cloud security, backup restore, operational, and privacy requirements have been reviewed.

## Configure and synthesize

Use Node from the repository `.nvmrc` and npm 11.21.1.

```powershell
npm ci --prefix infra/aws
Copy-Item infra/aws/cdk.config.example.json infra/aws/cdk.config.json
```

Edit `infra/aws/cdk.config.json` with the target AWS account and region, two Availability Zone names for that account/region, a bootstrap administrator email, an existing Route 53 hosted zone ID/name, and an ACM certificate ARN in the same account/region that covers both configured subdomains. The example values are placeholders and cannot be deployed. The config file is ignored by Git. CDK uses the normal AWS credential chain; credentials and secret values do not belong in the JSON file.

Synthesize the placeholder template locally:

```powershell
npm run verify:infra
```

`verify:infra` installs the isolated CDK package, typechecks it, runs template tests, and synthesizes using the example config. Synthesis does not deploy or contact AWS. To inspect the target configuration before deployment, bootstrap the account/region once and run:

```powershell
npm run diff --prefix infra/aws -- -c config=cdk.config.json
```

After reviewing the diff, deploy explicitly with:

```powershell
npm run deploy --prefix infra/aws -- -c config=cdk.config.json
```

Deployment builds Docker assets from the repository root and requires Docker plus AWS credentials with the necessary CDK, ECS, EC2, RDS, ElastiCache, S3, ACM, Route 53, IAM, Secrets Manager, and CloudWatch permissions. No deployment has been run as part of adding this code.

## Data and teardown

Database, Redis, and bootstrap super-admin passwords are generated by Secrets Manager and passed to ECS as task secrets. The configured admin email receives a generated password; read it from the `BootstrapAdminSecretArn` output through an approved AWS identity. RDS, its secret, the S3 bucket, logs, and Redis resources use retention safeguards. RDS automated backups are retained for seven days with deletion protection; Redis keeps one day of snapshots; S3 object versioning preserves prior Binary versions and delete markers. Restore RDS to a replacement instance from a point-in-time recovery or snapshot, attach it to the private data subnets/security group, verify the restored data, then update the CDK stack to use the replacement before shifting API tasks. Restore S3 object versions separately and check FHIR Binary references against the restored payloads. Test the recovery procedure in a non-production account before storing important data. Retained resources can continue to incur charges after the stack is removed; use an approved backup and cleanup procedure instead of relying on `cdk destroy` to remove them.

The server's FHIR Binary endpoints use S3 on this stack and filesystem storage in local/Docker configuration. There is no end-user medical-document upload/download screen, no cross-region replication, and no live AWS deployment yet. The API signs direct S3 download URLs with its ECS task role, so links remain valid across API task restarts until their expiry. The small single-AZ resources and one NAT gateway keep staging costs lower; enable multi-AZ and higher capacity only after workload and recovery requirements are measured.
